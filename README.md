# pgcollect

Инструмент read-only обхода кластера PostgreSQL 14+ (в основном 16). По каждой БД
собирает: обзор, схемы, роли/группы и их связи с объектами (членство + привилегии),
структуру таблиц (колонки, партиции, индексы, ограничения), анализ распухания
(bloat) таблиц/индексов/TOAST, качество автовакуума и свежесть статистики, а также
публикации логической репликации (какие таблицы в какие публикации входят). На каждую
БД генерирует **HTML-документ** и **документ для Confluence** (storage-format XML).

## Установка

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e .
```

## Права БД

Достаточно read-only учётки: суперпользователь ЛИБО роль с `pg_monitor` и правом
`CONNECT` на нужные БД. Все сессии открываются как `default_transaction_read_only=on`
с `statement_timeout`/`lock_timeout` — сбор ничего не меняет и ограничен по времени.
Для точного анализа bloat желательно расширение `pgstattuple` (иначе используется
оценочный метод по каталогу).

## Использование

```bash
cp targets.example.yaml targets.yaml   # заполнить подключения
export PGCOLLECT_PASSWORD=...           # пароль (имя переменной — из password_env)

# полный цикл: сбор + Confluence + HTML + Markdown для всех БД цели `local`
pgcollect all local

# по шагам:
pgcollect collect local            # → out/<db>.json
pgcollect render                   # out/<db>.json → out/<db>.confluence.xml
pgcollect preview                  # out/<db>.json → out/<db>.html
pgcollect markdown                 # out/<db>.json → out/<db>.md

# только одна БД / точный bloat / пропуск раздела
pgcollect all local --db billing --deep-bloat --skip roles
```

Артефакты в `out/`:

- `<db>.json` — сырые собранные данные (для отладки и дифов между прогонами);
- `<db>.confluence.xml` — вставляется в Confluence (редактор → «…» → `<>` вставка
  storage format);
- `<db>.html` — автономная страница для просмотра в браузере;
- `<db>.md` — Markdown-отчёт (для Git-репозиториев, wiki, code review).

Разделение `collect` и `render`/`preview` позволяет собрать данные один раз и
перегенерировать документы без повторного обращения к БД.

## Пропуск разделов (`--skip`)

Флаг `--skip` (у команд `collect` и `all`) отключает сбор отдельных разделов.
Можно указывать несколько раз: `--skip roles --skip bloat`. Раздел **Обзор**
(версия, размер, кодировка, расширения, cache hit ratio и т.п.) собирается всегда
и пропуску не подлежит.

| Значение          | Что пропускается                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| `schemas`         | Список схем (владелец, размер, число объектов).                                                      |
| `roles`           | Роли и членство, привилегии на объекты, **а также** привилегии по умолчанию (`ALTER DEFAULT PRIVILEGES`) — они тоже относятся к привилегиям. |
| `tables`          | Весь раздел «Таблицы»: колонки, партиции, **а также** индексы, ограничения, триггеры, автовакуум и bloat (они собираются внутри). |
| `bloat`           | Только оценка распухания таблиц/TOAST и фрагментации индексов (под-раздел внутри `tables`). Остальное по таблицам собирается. |
| `objects`         | Представления и матвью, функции/процедуры, пользовательские типы/домены, сторонние данные (FDW).     |
| `security`        | RLS-политики, привилегии по умолчанию (`ALTER DEFAULT PRIVILEGES`), event triggers. (Привилегии по умолчанию отключаются также через `--skip roles`.) |
| `publications`    | Публикации логической репликации (и обратная привязка публикаций к таблицам).                        |
| `extras`          | Доп. метрики: секвенции (риск исчерпания), долгие / idle-in-transaction, крупнейшие объекты, топ запросов (`--stat-statements`). |

Заметки:

- `bloat` — самый тяжёлый по нагрузке на БД раздел; пропускайте его (или `tables`
  целиком) на нагруженных кластерах, если оценка распухания не нужна.
- Пропуск `tables` неявно отключает и `bloat` (нет таблиц — нечего оценивать).
- «Сводку проблем» и производные метрики «Потенциальные проблемы»
  (таблицы без PK / без индексов, неиспользуемые индексы, FK без индекса)
  считаются из уже собранных данных таблиц, поэтому флагом `extras` **не**
  отключаются — они пропадут только вместе с `--skip tables`.
- Неизвестное значение в `--skip` игнорируется без ошибки (например, опечатка
  `--skip role` не отключит роли).

## Методика оценки bloat

Распухание (bloat) — это разница между фактическим размером таблицы/индекса на
диске и минимально необходимым для хранения живых строк. Оценивается гибридно:
дешёвый расчёт по каталогу для всех таблиц, точный замер по расширению — выборочно.

### 1. Оценочный метод (по умолчанию, для всех таблиц)

Запрос по системному каталогу (`pg_class` + `pg_stats`), адаптация общеизвестной
методики ioguix/check_postgres. Идея: по статистике планировщика оценить **среднюю
ширину строки** (`avg_width` с поправкой на `null_frac`), прибавить накладные
расходы (header кортежа, выравнивание по `MA` — 8 байт на 64-битных платформах),
и вычислить **ожидаемое** число страниц с учётом `fillfactor`:

```
est_tblpages_ff = ceil( reltuples / ((block_size − page_hdr) · fillfactor / (tpl_size·100)) )
                  + ceil( toasttuples / 4 )
bloat_bytes     = (tblpages − est_tblpages_ff) · block_size
bloat_pct       = 100 · (tblpages − est_tblpages_ff) / tblpages
```

Свойства и ограничения:

- **Лёгкий** — только каталог, БД не сканируется; подходит для любого размера.
- **Приблизительный** — точность зависит от свежести `ANALYZE`: если статистика
  устарела, `reltuples`/`avg_width` врут и оценка тоже. Учитывает heap + TOAST-страницы.
- Для строк, где оценка невозможна (колонки типа `name`, скрытые/системные
  атрибуты), запрос выставляет флаг `is_na` → статус bloat `unknown` (не считаем).
- Оценивается только heap (+TOAST); фрагментация индексов этим методом не измеряется.

### 2. Точный метод (`pgstattuple`, выборочно)

Если в БД установлено расширение `pgstattuple`, для таблиц берётся реальный
процент через `pgstattuple_approx()` (`approx_free_percent + dead_tuple_percent`) —
он **переопределяет** оценку и метод в отчёте помечается как `pgstattuple`.
Для btree-индексов через `pgstatindex()` считается распухание
(`100 − avg_leaf_density`) и фрагментация листьев (`leaf_fragmentation`).

Эти функции **читают объект целиком**, поэтому вызываются не для всех:

- по умолчанию — только для объектов не крупнее `pgstattuple_max_mb` (512 МБ);
- флаг `--deep-bloat` снимает порог и запускает точный замер для **всех** объектов
  (может быть тяжёлым для БД — использовать осознанно, лучше на реплике/в окно).

Без расширения `pgstattuple` работает только оценочный путь (п.1).

### Флаг `--deep-bloat`

Флаг команд `collect` и `all` (по умолчанию **выключен**). Управляет тем, для
каких объектов запускается точный `pgstattuple`:

- **без флага** — точный замер только для объектов не крупнее `pgstattuple_max_mb`
  (512 МБ); крупнее — остаётся оценка по каталогу;
- **`--deep-bloat`** — порог по размеру снимается, точный `pgstattuple` /
  `pgstatindex` запускается для **всех** таблиц и индексов независимо от размера.

Предостережения:

- нужен `pgstattuple` в БД — без расширения флаг ничего не даёт;
- эти функции **сканируют объект целиком** (полное физическое чтение всех
  страниц, вытеснение shared buffers, нагрузка на диск) — на крупных объектах
  ощутимо. Именно поэтому по умолчанию флаг выключен, а порог 512 МБ ограждает
  от тяжёлых сканов;
- запускайте осознанно: на **реплике** или в **обслуживающее окно**, а не на
  нагруженном мастере в пик.

Типичный сценарий: оценочный метод показал подозрительный или `unknown` bloat на
крупной таблице — перепроверить точно перед `VACUUM FULL` / `REINDEX`:

```bash
pgcollect all local --db billing --deep-bloat
```

### Пороги и статусы

Процент bloat превращается в статус ok/warn/crit по порогам из `thresholds`
в `targets.yaml` (значения по умолчанию):

| Порог               | Default | Смысл                                              |
| ------------------- | ------- | -------------------------------------------------- |
| `bloat_warn_pct`    | `20`    | ≥ этого — **warn**                                 |
| `bloat_crit_pct`    | `40`    | ≥ этого — **crit** (кандидат на `VACUUM FULL`/`REINDEX`) |
| `pgstattuple_max_mb`| `512`   | выше — точный `pgstattuple` не вызывается без `--deep-bloat` |

Таблицы/индексы со статусом warn/crit попадают в «Сводку проблем» вверху отчёта.

## Риск wraparound

Возраст `age(relfrozenxid)` таблицы сравнивается с **реальным горизонтом
wraparound — 2³¹ ≈ 2.15 млрд транзакций** (`config.py`, `wraparound_warn_pct` /
`wraparound_crit_pct`; по умолчанию warn при ~50% ≈ 1.07 млрд, crit при ~75% ≈
1.61 млрд, что совпадает с `vacuum_failsafe_age`).

Важно: `autovacuum_freeze_max_age` (по умолчанию 200 млн) — это **не** граница
wraparound, а порог, при котором PostgreSQL **форсирует anti-wraparound
autovacuum**. Достичь и слегка превысить его — штатное поведение (таблица
замораживается и `age` сбрасывается), поэтому само превышение риском **не**
считается. Отдельным мягким сигналом «Autovacuum отстаёт (freeze)» отмечаются
таблицы, где `age` превысил `freeze_max_age` **кратно** (≥ 2×) — это значит, что
форсированный freeze-autovacuum не справляется, и стоит разобраться.

> Если в отчёте стоит «Риск wraparound», сверьтесь на самой БД:
> `SELECT c.oid::regclass, age(c.relfrozenxid) FROM pg_class c
> WHERE c.relkind IN ('r','m') ORDER BY 2 DESC LIMIT 20;`
> Тревога реальна при `age` порядка ~1.5–2 млрд, а не сотен млн.

## pgservercollect — отчёт по кластеру (instance-wide)

Второй инструмент того же пакета. `pgcollect` собирает картину **по каждой БД**,
`pgservercollect` — **глобальное состояние экземпляра/кластера** через одно read-only
подключение к postgres: идентичность, конфигурацию (с таблицей оптимизации), физическую
топологию репликации, WAL/архивацию, активность, чекпоинты, локи, tablespaces, роли,
подписки, prepared-транзакции. Артефакт — один на кластер:
`out/cluster.<target>.{json,confluence.xml,html,md}`.

```bash
pgservercollect all local            # collect + render + preview + markdown
pgservercollect collect local        # только out/cluster.local.json
pgservercollect all local --skip progress --skip locks
```

Права: базовый охват — роль с `pg_monitor` (репликация, полная активность, слоты);
суперпользователь нужен лишь для будущего раздела pg_hba. Недоступные из-за прав разделы
не роняют прогон, а уходят в предупреждения.

### Таблица оптимизации конфигурации

В отчёт входит таблица «параметр → **дефолт** (`boot_val`) → **текущее значение** →
**рекомендация**» с колонками «почему», «основание» и приоритетом. Основание бывает трёх
видов: `по вводным` (посчитано от железа/нагрузки из `targets.yaml`), `по данным PG`
(обосновано рантайм-статистикой — temp_files, req-checkpoint, cache hit) и `ориентир`
(best-practice/формула без точных вводных).

PostgreSQL по SQL не знает объём RAM/CPU/тип диска, поэтому для **числовых** рекомендаций
(shared_buffers и т.п.) железо задаётся вручную. Опишите узлы кластера массивом `nodes`
и общий профиль нагрузки `workload`:

```yaml
    workload:
      kind: oltp                 # oltp | olap | mixed
      connections: 100           # ожидаемое число одновременных соединений
    nodes:
      - name: pg1
        role: leader             # leader | replica
        cpu: 8                   # число ядер
        mem: 16GB                # "16GB" / "16384MB" / 16384 (число = МБ)
        disk_type: ssd           # ssd | hdd | nvme
      - name: pg2
        role: replica
        cpu: 8
        mem: 16GB
        disk_type: ssd
```

Рекомендации считаются от ресурсов **leader-узла** (в кластере конфиг единый, его задаёт
нагрузка на primary), независимо от того, к какому узлу подключились, — поэтому пометьте
leader-узел `role: leader`. Если leader не помечен, железо берётся авто-подбором по
подключённому экземпляру (единственный узел → GUC `cluster_name` члена → имя цели
`target.name` → явное поле `node`); иначе — падение на ориентир с поясняющей заметкой.

`work_mem` считается как `≈25% RAM / workload.connections` — от **ожидаемого** числа
соединений, а не от завышенного `max_connections`. Если `workload.connections` не задан,
делитель берётся из `max_connections` и в отчёт добавляется предупреждение.

Для одиночного (не кластерного) сервера можно вместо `nodes` задать один блок `hardware`
(`total_ram_mb` / `cpu_count` / `storage_type`).

Без этих вводных рекомендации остаются формулой-ориентиром, а инструмент печатает
предупреждение (в stderr и баннером в отчёте) с перечнем недостающих полей.

### Потребление ОЗУ по компонентам

Отдельный раздел отчёта — оценка потребления RAM по **текущим настройкам** кластера,
разложенная по компонентам/процессам (`shared_buffers`, `wal_buffers`, прочие разделяемые
структуры, maintenance/autovacuum-пул, базовый оверхед backend'ов, `work_mem`,
`temp_buffers`) в **трёх сценариях**:

| Сценарий | Соединения | `work_mem` на backend | Что показывает |
| --- | --- | --- | --- |
| **Минимальное** | текущее число backend'ов (`pg_stat_activity`) | 0 (простой) | «пол» потребления сейчас |
| **Среднее** | текущее число backend'ов | 1 аллокация | типичное текущее потребление |
| **Максимальное** | `max_connections` | до 3 аллокаций + `temp_buffers` | «потолок» при насыщении |

Разделяемая память и maintenance-пул одинаковы во всех сценариях; различие — в числе
соединений и интенсивности `work_mem`. Если задан `mem` у leader-узла — считается доля от
ОЗУ, и при превышении максимальным сценарием объёма RAM выводится предупреждение об OOM.
Точный объём прочей разделяемой памяти берётся из `pg_shmem_allocations` (нужен
superuser/`pg_read_all_stats`); без прав раздел деградирует к `shared_buffers + wal_buffers`
с пометкой. Базовый оверхед backend'а — приблизительная оценка. Отключается `--skip memory`.

### Про Patroni

Раздел «Репликация» строит **фактическую** топологию по данным PostgreSQL
(`pg_stat_replication`, `pg_stat_wal_receiver`, `pg_replication_slots`, лаг, sync-состояние).
Это не состояние Patroni/DCS: через PG-подключение недоступны авторитетный лидер по DCS,
лежащие узлы, теги/приоритеты членов, история failover и DCS-конфигурация — они живут в
etcd/Consul/ZooKeeper и Patroni REST API. Отчёт это явно оговаривает.
